# 变更协议

PRD 流程完成后，用户提出新需求/变更时的处理规则。**只从变更落点向下游重跑，禁止全量重跑。**

## 触发条件

进度文件「闸口状态」为「已完成」，且用户提出：
- 新增/删除功能
- 修改已确认的业务流程或规则
- 原型/PRD 已定稿后的调整

## 处理流程

1. **拆解变更句**：把用户的变更描述拆成具体变更点。
2. **定位落点**：判断变更影响哪个阶段的产物。
   - 影响业务流程/功能模块/用户场景 → 落点 = 阶段1（概要PRD）
   - 仅影响页面交互/布局 → 落点 = 阶段2（原型）
   - 仅影响字段规则/状态/边界 → 落点 = 阶段5（详细PRD）
3. **向下游重跑**：从落点阶段开始，只更新受影响的产物，下游阶段跟着刷新。
   - 落点阶段1 → 概要PRD改 → 原型改 → 反馈/评审补 → 详细PRD改 → 研发评审重出
   - 落点阶段2 → 原型改 → 后续跟进
   - 落点阶段5 → 详细PRD改 → 研发评审重出
4. **R/C-编号顺延**：确认记录与变更项继续追加，不清零历史。

## 落点判断示例

```
变更「加一个批量导出功能」
→ 新功能 = 落点阶段1（概要PRD加模块+页面）
→ 原型加导出交互（阶段2）
→ 详细PRD补导出的字段/权限/异常（阶段5）
→ 研发评审重估工量（阶段6）

变更「导出按钮挪到右上角」
→ 纯交互 = 落点阶段2（改原型即可）
→ 若已有详细PRD引用该页面，同步一句话

变更「导出上限从1万条改5万条」
→ 规则调整 = 落点阶段5（改详细PRD的字段规则）
→ 研发评审重估（阶段6，可能触发性能风险）
```

## 禁止

- 全量重跑所有阶段（浪费且丢失历史）
- 跳过拆解直接改详细PRD
- 变更原型却不同步详细PRD（导致原型与PRD脱节）
- 清空 R/C-编号历史
