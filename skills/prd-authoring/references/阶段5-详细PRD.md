# 阶段5：详细 PRD + 最终原型

**产物**：`05-详细PRD.md` + 更新后的 `prototype/`（最终版）

**目标**：根据阶段4用户裁决，先更新原型，再把概要PRD + 最终原型 + 用户反馈 + 评审，收敛成**研发可直接读的详细PRD**。字段级、状态级、规则级都要讲清。

## 执行动作

1. **读阶段4用户裁决**：`04-用户视角评审报告.md` 的「## 用户裁决」段，提取用户接受的问题（R-编号）及指定改法
2. **更新原型**（若用户裁决要求改）：
   - 按用户指定改法修改 `prototype/` 下对应页面
   - 改完在对话向用户确认「原型已按 R-XXX 改完，请点击 prototype/index.html 验收」
   - 用户确认 OK 后继续
3. **读齐上游产物**：`02-概要PRD.md`、最终 `prototype/`、`03-原型试用反馈.md`（若有）、`04-用户视角评审报告.md`
4. **先做回填表**（铁律）：把阶段3反馈 + 阶段4评审的每一条，逐条标注处理方式（已解决/暂缓/不采纳），写进详细PRD的「评审回填」章节
5. **逐功能模块展开详细需求**：功能描述、交互流程、字段规则、状态流转、边界与异常
6. 对原型已体现的交互，引用原型页面（"见 prototype/xxx.html"），不重复画
7. 业务规则有空缺 → 对话共创（禁止 AI 脑补规则）
8. 写入 `05-详细PRD.md`
9. 停在闸口

## 回填要求（铁律3，最重要）

详细PRD**必须**有一章逐条回应上游评审，每条给结论：

| 来源 | 编号 | 问题 | 处理 | 说明 |
|---|---|---|---|---|
| 用户反馈 | F-01 | ... | 已解决/暂缓/不采纳 | 在PRD哪节体现/为何不采纳 |
| 视角评审 | E-01 | ... | 已解决/暂缓/不采纳 | ... |

**禁止**：无视评审结论，另写一份和评审脱节的PRD。

## 共创要求

详细PRD 涉及大量业务规则（校验规则、状态流转、权限矩阵、异常处理）。对每个规则空缺：
- 在对话展示问题 + 建议默认值
- 拿到用户方向再写入，标 `[已确认-R编号]`
- 允许"先按默认，后续可调"，但不允许 AI 编造硬规则当成需求

## 闸口话术

```
【阶段5完成】详细PRD已写入 outputs/<产品名>/04-详细PRD.md

一、PRD结论：
- 详细展开 N 个功能模块
- 回填上游评审 M 条（已解决X/暂缓Y/不采纳Z）
- 明确边界 K 项

二、待你裁决：
1. 详细需求准确吗？有没有理解偏差的规则？
2. 评审回填的处理方式（暂缓/不采纳项）你认可吗？
3. 字段规则、状态流转有没有要补的？

三、确认后进入阶段6：研发需求评审（技术可行性/工量/边界/依赖/风险）
```
