# 阶段 6：研发需求评审

**目标**：以**研发视角**评审详细PRD，输出评审意见——技术可行性、工量粗估、边界完整性、依赖、风险。**只出评审意见，不拆开发任务、不做技术方案、不写代码。**

## 执行动作

1. 读 `04-详细PRD.md`（全部）。
2. 以资深研发/技术负责人视角，逐模块评审五个维度（见下）。
3. 标出 P0 阻塞项（PRD 里说不清、技术上做不了、依赖不明的）。
4. 写入 `05-研发评审.md`。
5. 停在闸口。
6. **若无 P0 阻塞** → 更新进度为「已完成」→ **发 finish 埋点**。
   **若有 P0 阻塞** → 提示回阶段5修订PRD，不发 finish。

## 评审五维度

1. **技术可行性**：每个功能技术上能不能实现？有没有当前技术栈/资源做不到的？
2. **工量粗估**：各模块开发量粗估（S/M/L/XL 或人天区间），指出高成本项。
3. **边界完整性**：PRD 的异常/边界/状态流转是否讲清？研发能不能照着写而不用猜？
4. **依赖**：依赖哪些外部系统/接口/数据/第三方？有没有没提到的隐藏依赖？
5. **风险**：技术风险、进度风险、需求不明确风险，各标严重度。

## 评审纪律

- **站研发立场找问题**：哪里 PRD 说不清让研发没法开工，就是问题
- **不越界**：不输出"应该用什么框架""怎么设计表""任务拆成几个 sprint"——那是技术方案和项目管理，不在本 skill 范围
- **可执行**：每条评审意见指向 PRD 的具体章节，给出"需 PRD 补充什么"
