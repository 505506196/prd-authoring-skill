# 阶段6：三审·研发需求评审（独立子代理）

**产物**：`05-研发评审.md`

**目标**：三审的第三审。派**独立 subagent**以研发/技术负责人视角评审详细PRD草稿+原型——技术可行性、工量粗估、边界完整性、依赖、风险。**只出评审意见，不拆开发任务、不做技术方案、不写代码、不决策不修改**（改在阶段7）。

**铁律**：用独立 subagent（技术视角客观）；只出意见，决策统一到阶段7。

## 执行动作

1. 用 Agent 工具启动独立 subagent，传入评审任务（见下方协议），评审对象 = `02-详细PRD草稿.md` + `prototype/`。
2. subagent 产出评审意见，主对话写入 `05-研发评审.md`。
3. 在对话向用户展示 TOP 问题 + P0 阻塞项（**只告知，不决策**）。
4. 停在闸口。**本阶段不发 finish**（finish 在阶段7交付时发）。

## subagent 调用协议

用独立 subagent（通用型），任务提示：

```
你是资深研发/技术负责人，评审一份准备进入开发的需求。

评审对象：
- 详细PRD草稿：outputs/<产品名>/02-详细PRD草稿.md
- 原型：outputs/<产品名>/prototype/

逐模块评审五个维度：
1. 技术可行性：每个功能技术上能不能实现？有没有当前技术栈/资源做不到的？
2. 工量粗估：各模块开发量粗估（S/M/L/XL 或人天区间），指出高成本项。
3. 边界完整性：PRD 的异常/边界/状态流转讲清了吗？研发能照着写而不用猜吗？
4. 依赖：依赖哪些外部系统/接口/数据/第三方？有没有没提到的隐藏依赖？
5. 风险：技术风险、进度风险、需求不明确风险，各标严重度。

纪律：
- 站研发立场找问题：哪里 PRD 说不清让研发没法开工，就是问题
- 不越界：不输出"用什么框架""怎么设计表""拆几个 sprint"——那是技术方案和项目管理
- 可执行：每条意见指向 PRD 具体章节，给出"需 PRD 补充什么"

输出格式：
## P0 阻塞项（不解决无法开工）
| 编号 | 阻塞点 | 指向PRD章节 | 需补充什么 |
|---|---|---|---|
| D-01 | 报名并发未定义 | 3.2 | 补高峰并发量和排队策略 |

## 技术可行性
| 模块 | 可行性 | 说明 |
## 工量粗估
| 模块 | 粗估量 | 高成本点 |
> 总量粗估：<区间>
## 边界完整性
| 模块 | 缺失的边界/异常/状态 | 需PRD补充 |
## 依赖
| 依赖项 | 类型 | 是否明确 | 备注 |
## 风险
| 编号 | 风险 | 类型 | 严重度 | 应对建议 |
```
